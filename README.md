**Исходники:** https://github.com/MeldanLess/kopilka

Личный финансовый трекер на полном стеке: FastAPI + PostgreSQL на бэкенде,
React + TypeScript на фронтенде. Это третий проект портфолио и самый
применимый: всё, что в нём есть, я делаю для себя — считаю свои деньги по
категориям и смотрю, куда они уходят.

Интересен он не предметной областью, а тем, как решены вещи, которые обычно
решают «как получится»: деньги не проходят через `float`, чужие данные
невозможно увидеть даже по ошибке, а суммы за месяц считает база, а не
JavaScript.

---

## Что он умеет

| Возможность | Как это выглядит |
|---|---|
| Регистрация и вход | OAuth2 password flow, пароли — bcrypt-хеши, токен — JWT |
| Доходы и расходы | Одна форма, категория выбирается из списка своего вида |
| Категории | Свои у каждого человека, с цветом для диаграммы; при регистрации — готовый набор |
| Сводка по месяцу | Доходы, расходы, остаток и разрез по категориям с долями |
| Графики | Круговая диаграмма «куда ушли деньги» и столбчатая динамика за полгод |
| Выгрузка в CSV | Файл, который открывается в русском Excel двойным щелчком |
| Изоляция данных | Операции и категории одного человека не видны другому |

**Правила, которые обеспечивает сервер:**

- Сумма всегда положительная: **знак задаёт вид операции**, а не пишется
  отдельно. Нет операции «−500 ₽» — есть расход в 500 ₽.
- Категория расходов не может оказаться у дохода — это **409**, а не 404:
  категория существует, несовместима она.
- Вид категории менять нельзя: он определяет, доходом или расходом была
  операция, и смена вида сломала бы уже записанные операции.
- Категорию с операциями удалить нельзя — иначе суммы за месяц посчитались бы
  не полностью.
- Чужие данные возвращают **404, а не 403** — 403 подтвердил бы, что такой
  идентификатор существует.

## Стек

| Слой | Выбор | Почему |
|---|---|---|
| Бэкенд | FastAPI 0.115 | Тела запросов, проверенные типами, и OpenAPI-схема, генерируемая из кода |
| Валидация | Pydantic v2 | Один слой схем и на вход, и на выход; ORM-модели не торчат наружу |
| ORM | SQLAlchemy 2.0 | Типизированные `Mapped[...]`, стиль 2.0 — нынешний общепринятый |
| Миграции | Alembic | История схемы — источник истины, а не `create_all` |
| База | PostgreSQL 16 | Нативные типы `enum`, колонки `UUID`, `NUMERIC` для денег, `ILIKE` |
| Аутентификация | PyJWT + bcrypt | `bcrypt` вызывается напрямую: `passlib` не поддерживается с 2020 года |
| Фронтенд | React 18 + TypeScript | Типы на границе с сервером — из общих контрактов, а не «на глаз» |
| Графики | Recharts | Декларативно и умеет в SVG; для двух диаграмм этого достаточно |
| Сборка | Vite | Быстрый dev-сервер и сборка без конфигурации |
| Тесты | pytest + Vitest | Один и тот же стиль тестов на обоих концах стека |
| Развёртывание | Docker + Compose | Один `docker compose up` поднимает всё: база, API и фронтенд |

## Решения и размены

Здесь — то, что обычно спрашивают на собеседовании: почему именно так.

### 1. Деньги — это `NUMERIC(14, 2)` и `Decimal`, а не `float`

Двоичная точка не умеет хранить десятую долю копейки. Ошибка округления в
сумме — это ошибка в зарплате. `NUMERIC` в PostgreSQL и `Decimal` в Python
хранят ровно то, что написано, и сложение не накапливает погрешность.

Поэтому сумма приходит в JSON **строкой** (`"1234.56"`), а не числом: если бы
она превратилась в IEEE 754, клиент сложил бы её и получил
`1234.5599999999999`. На фронтенде сумма тоже не превращается в число при
выводе — разряды расставляются регулярным выражением по строке.

**Размен:** приходится вручную разбирать сумму в формах и нельзя просто
сложить две строки. Зато сумма на экране всегда совпадает с суммой в базе.

### 2. Вид операции лежит рядом с суммой, а не выводится из категории

Дублирование данных — осознанное решение. Категория задаёт *вид* операции, а
поле `kind` у транзакции — это её *собственный* вид, и согласованность между
ними проверяется при записи и при изменении.

**Размен:** дублирование, которое придётся поддерживать. Зато сводка по
месяцу не требует соединения с таблицей категорий, а вид операции нужен
почти везде: в списке, в фильтрах, в экспорте, в графиках.

### 3. Виды — нативные `enum` в PostgreSQL, а не `varchar`

`varchar` принимает любое значение: опечатка в коде или ручной `UPDATE` тихо
портит данные, и потом нельзя понять, что именно сломалось. Нативный `enum`
отвергает такое значение на уровне базы. Второе следствие — новое значение
требует миграции, и это видно в истории.

### 4. Токен лежит в `localStorage`, а не в cookie

`localStorage` доступен JavaScript, поэтому токен можно выкрасть через XSS.
Взамен не нужно разбираться с `SameSite`, `Secure` и с тем, как cookie
переживает перезагрузку страницы.

**Размен выбран в пользу простоты** и осознанно ограничен приложением, в
котором в токене нет ничего, кроме идентификатора пользователя. Для
банковского приложения нужно `HttpOnly`-cookie и защита от CSRF — и это другой
уровень требований, а не «чуть-чуть другой код».

### 5. Данные перезагружаются целиком, а не точечно

После любого изменения перечитываются сводка, список, категории и графики.
Для трекера с сотнями операций это честный размен: сложное частичное
обновление даёт выигрыш в миллисекундах, а взамен появляется рассинхрон между
списком, сводкой и диаграммой — а это уже настоящая ошибка, которую увидит
человек.

### 6. Тесты идут против настоящего PostgreSQL

SQLite запускается быстрее, но не умеет ни колонки `UUID`, ни нативные типы
`enum`, ни `NUMERIC` для денег, ни ограничения внешних ключей с `RESTRICT`.
То есть именно то, что и нужно проверять, SQLite проверять не даст.

**Размен:** тесты медленнее и требуют сервиса в CI. Зато набор тестов
поднимает настоящую базу, накатывает на неё миграции Alembic (то есть под
тестом оказывается и сама миграция) и чистит её между тестами.

### 7. CSV готов к русскому Excel, а не к «как получится»

Разделитель `;`, десятичная запятая и `BOM` в начале файла — без `BOM` Excel
считает файл в CP1251 и кириллица превращается в мусор. Имя файла содержит
период, а в имени — только латиница: имя попадает в заголовок
`Content-Disposition`, а заголовки HTTP кодируются в latin-1, и кириллица
превратила бы ответ в 500.

### 8. Ошибка — одна форма на весь API

Каждое тело ошибки содержит `detail`, `status_code`, `path` и `request_id`.
Идентификатор запроса возвращается и в заголовке `X-Request-ID`: человек,
сообщающий о проблеме, может назвать значение, которое совпадёт со строкой в
логе.

## Как запустить

```bash
git clone https://github.com/MeldanLess/kopilka.git
cd kopilka
docker compose up --build
```

* Фронтенд — <http://localhost:5173>
* API и документация — <http://localhost:8000/docs>

Демо-данные (аккаунт `demo@example.com`, пароль `demo12345` и операции за
последние три месяца):

```bash
docker compose exec api python -m app.seed
```

### Бэкенд отдельно

```bash
cd backend
cp .env.example .env
docker compose up --build      # PostgreSQL + API
pip install -r requirements-dev.txt
pytest --cov=app --cov-report=term-missing
```

### Фронтенд отдельно

```bash
cd frontend
npm ci          # точные версии зависимостей из package-lock.json
npm run dev
```

## Структура

```
kopilka/
├── backend/            FastAPI, SQLAlchemy, Alembic, pytest
│   ├── app/
│   │   ├── routers/    HTTP-слой: только разбор запроса
│   │   ├── crud.py     весь SQL живёт здесь
│   │   ├── models.py   ORM: users, categories, transactions
│   │   └── schemas.py  схемы Pydantic — публичный контракт
│   ├── alembic/        миграции
│   └── tests/          набор тестов против настоящей базы
├── frontend/           React, TypeScript, Vite, Vitest, Recharts
│   ├── src/
│   │   ├── api/        типизированный клиент, ни одного URL в компонентах
│   │   ├── auth/       контекст аутентификации и хранение токена
│   │   ├── components/ экраны и виджеты
│   │   └── utils/      форматирование денег и работа с месяцами
│   └── tests/
└── docker-compose.yml  база + API + фронтенд одной командой
```

## Что не сделано

Честный список на будущее — чтобы не выдавать желаемое за сделанное:

- Несколько валют и обменные курсы.
- Регулярные операции («каждый месяц 8 000 ₽ за аренду»).
- Мобильное приложение.
- Импорт из банковских выписок.
- Ограничение частоты запросов на вход (rate limiting).
- Сквозной E2E-тест основного сценария — сейчас бэкенд и фронтенд проверяются
  по отдельности, и связка между ними не покрыта. Как это сделать, обсуждается
  в [issue #1](https://github.com/MeldanLess/kopilka/issues/1).
